# MarketAgent 审查与修改建议

审查日期：2026-10-29（纽约时间）  
仓库：https://github.com/vvveronica1122/market-agent  
审查版本：`d07fe2b96b1beb80c62d218f5118f6e8ec7fbaa7`

> 本文是修改计划，不代表以下修复已经完成。依据为代码、仓库截图、测试、评估记录和回测报告。已运行 `python run_tests.py`，10 个离线测试套件全部通过；另做了模拟故障和模型输出检查。未重新运行付费模型评估、实时行情验证或完整浏览器交互测试。后续实施前应对照最新代码确认问题是否仍存在。

## 1. 总体判断与修改目标

项目已经展示了数据接入、工具调用 agent、确定性计算、LLM 解释、前端与评估的完整实现。主要不足是：功能广度超过了核心排序的验证深度，数据失败状态不够明确，部分输出限制缺少可靠的运行时保障，尚未证明能为目标用户节省时间。

下一版本的目标：**用户能更快找到值得关注的变化，重要结论能追溯到数据，数据或模型失败时不会给出看似完整的判断。**

### 应保留的设计

- 排序和数值计算由 Python 完成，LLM 负责解释与自然语言交互。
- Ask 的工具选择、执行、结果回传、多步调用和轮次限制。
- ETF 与排除自身后的同行中位数双重比较，以及最少同行数量限制。
- 离线测试、CI、失败案例、评估结果记录和 judge 稳定性检查。
- 静态 demo 构建方式，以及明确标注快照、只读与录制回放的做法。

## 3. P0：数据状态与降级行为

### 问题依据

- `tools/market_data.py` 的新闻查询失败可能返回空列表；事件查询失败可能返回空日期。
- `web/app.py` 的 `safe()` 与 `fetch_row()` 使用默认值继续计算。
- 本地验证：`compute_attention(None, [], {}, None)` 返回 `score=0.0`、`level="quiet"`。
- 价格错误在部分界面另有提示，但新闻或事件接口失败仍可能不易察觉，且影响评分。

“确实没有新闻”“数据源没有提供新闻”“请求失败”应有不同状态。

### 修改方法

1. 为各数据域定义明确的数据契约，例如：

```json
{
  "status": "ok",
  "data": [],
  "as_of": "2026-10-29T20:00:00Z",
  "source": "provider_name",
  "error_code": null
}
```

`status` 至少区分 `ok`、`empty`、`error`、`stale`。字段粒度可以按行情、新闻、事件分别管理，不必强行包装所有内部计算函数。

2. 关键输入不足时，关注度标记为 `unknown` 或“不完整”，不要给出完整的 quiet 判断。
3. 如果仍展示部分评分，标注哪些分项不可用，避免用户直接比较信息完整度不同的股票。
4. 将数据状态传入 LLM；前端用用户能理解的说明表达缺失原因。
5. 明确缓存数据时间与行情所属交易时段，避免不同时间的数据被当成同一快照。

### 验收标准

- [ ] 新闻接口成功但为空，与接口失败，在 API 和界面中可区分。
- [ ] 财报接口失败不会被解释为“没有即将发生的财报”。
- [ ] 关键数据缺失时不会显示完整可靠的 quiet 结论。
- [ ] 模拟单个数据源超时或异常，页面仍可使用，并标明缺失部分。
- [ ] 模型不会把缺失输入当作已验证的否定事实。

## 4. P0：输出校验与结构化数据

### 问题依据

`web/app.py::without_multiples()` 检测到违规倍数表达后请求一次改写；改写失败或仍违规时，会返回原文。现有测试也要求这种行为。模拟改写接口失败后，已确认违规原文被返回。

`extract_themes()` 缺少完整字段和集合约束。模拟验证结果：

- 输入只有 NVDA，输出中的 `MADEUP` 仍被接受。
- 模型返回 `"tickers": 42` 时抛出 `TypeError`。

### 修改方法

1. 校验未通过时，回退到由代码生成的简短事实摘要；保留原文供内部诊断，不作为默认展示内容。
2. 定义结构化输出 schema，检查根类型、字段类型、长度和必填字段。
3. 校验主题中的 ticker 必须属于本次输入的候选集合；对异常项过滤或整体降级，并记录原因。
4. 对数字与比较关系，优先使用代码计算好的结果。正则检查仅能覆盖特定表达，不能充当事实校验器。
5. 更新现有测试的预期：错误规则本身需要改变，不能只追加测试数量。

### 验收标准

- [ ] 改写失败、空字符串或再次违规时，展示有效的事实降级文本。
- [ ] 不存在于候选集合的 ticker 不会进入展示结果。
- [ ] `tickers` 为数字、字符串、对象或 null 时，不会导致未处理异常。
- [ ] 正常输入行为保留，异常结果可以追踪。

## 5. P0：财报分析的统计解释

### 问题依据

`web/app.py` 的分析提示词将 abnormal move 描述为 “it isolates the reaction to the report”。扣除历史 beta 与 SPY 所解释的变化，不能排除行业事件、其他公司消息和模型误差，因此不支持这个因果结论。

`tools/performance.py` 估计 alpha，但计算 expected return 时主动省略 alpha。代码说明了理由；这是一项需要明确披露并验证敏感性的建模选择。

### 修改方法

- 把措辞改成“财报附近，超出历史市场联动关系所解释部分的涨跌”。
- 在界面说明 beta 调整后的收益具体如何计算，避免把剩余收益全部归因于财报。
- 对包含 alpha、仅使用 beta、使用行业基准的结果做敏感性比较；暂时不必一次上线所有模型。
- 标准化收益用于描述异常程度；如果要解释为正式统计显著性，需要另行处理假设与估计不确定性。

### 验收标准

- [ ] 提示词与界面不再声称已隔离财报的因果影响。
- [ ] 公式、alpha 处理、估计窗口和数据不足条件有明确说明。
- [ ] 至少选择若干实际事件比较不同设定，并记录结论是否改变。

## 6. P1：重新定义与验证 attention score

### 问题依据

仓库 `validation/attention-2026-10.md` 报告了 19 家公司、439 个交易日的回测。新闻项因缺少历史数据而未参与回测。

| 方法 | 首位股票具有组内最高异常成交量的比例 |
| --- | ---: |
| 当前综合评分，不含新闻项 | 42% |
| 绝对涨跌幅 | 41% |
| 波动率标准化涨跌幅 | 43% |
| 随机选择 | 22% |

综合评分相对原始涨跌幅存在小幅 IC 增益，但相对简单方法的实际使用价值仍需验证。报告同时发现高波动偏好、财报反应日失去事件加分、新闻计数几乎不区分公司等问题。当前实现仍保留这些规则。

### 修改方法

1. 拆分两类任务：
   - **今日异常**：相对自身波动率的变化、同行偏离、异常成交量等。
   - **未来事件**：财报与其他需要准备的日期，独立展示。
2. 比较当前评分、简单涨跌幅、波动率标准化涨跌幅及少量改进方案。先明确目标，不为了最大化单一代理指标堆叠特征。
3. 新闻只统计明确时间窗口内的信息，并去重；若无法获得可靠历史新闻，不将无新闻回测结果描述为完整线上评分的验证。
4. 对财报报告日及反应交易日建模，区分盘前和盘后；时间未知时明确标记。
5. 在新数据或事先锁定的时间留出集上验证。已被用于形成修改建议的样本不能再充当全新测试集。
6. 关注度等级应有稳定含义，例如相对历史异常程度；通过展示频率检查阈值是否过于宽松。

### 验收标准

- [ ] 未来事件提醒与今日异动在语义和展示上明确区分。
- [ ] 有基线比较、分项消融和按股票分组的结果。
- [ ] 保留失败结论；没有稳定增益的复杂分项可以删除。
- [ ] 每个排名有可解释理由，且理由与实际参与计算的数据一致。
- [ ] 报告明确区分历史样本表现、样本外表现与用户价值。

## 7. P1：评估覆盖面与运行观测

现有 brief guard 的 0/48 来自两个场景各重复 24 次，衡量特定倍数表达规则。这个结果有回归验证价值，但不等于一般事实错误率为零。生成与 judge 使用同一模型，也可能有共同盲点；稳定性检查不能消除全部偏差。

### 修改方法

- 扩展不同日期、公司、市场状态与任务的场景。
- 加入新闻过期、事件日期缺失、输入矛盾、工具部分失败、结构化输出异常等情况。
- 人工核对一批答案，标出重要事实与支持证据，分析 judge 的误报和漏报。
- 将确定性规则通过率、人工事实正确率、judge 分数和任务完成率分别报告。
- 记录延迟、模型调用次数、token 或实际费用、工具失败率与降级率。
- 当前 agent trace 主要保留工具名和输入；增加必要的结果摘要、数据时间、状态和耗时，支持答案核对。默认界面可以折叠技术细节。

### 验收标准

- [ ] 报告同时说明场景数量与重复次数。
- [ ] 有未参与调优的新场景，以及人工审查样本。
- [ ] 模型或提示词变化后，可以比较事实质量、成本和延迟。
- [ ] 至少能从重要结论追溯到对应的数据结果或来源。

## 8. P1：首页、加载体验与用户验证

### 问题依据

仓库截图中，首页长篇 AI brief 占据较多首屏空间，移动端尤其明显。用户需要先阅读大量文字，才能看到关注对象。

`web/app.py::stock_detail()` 在返回整页数据前调用 `analyze()`，因此个股价格、图表等内容也会等待模型分析完成。此处依据代码依赖关系，尚未实测真实加载时间。

### 修改方法

1. 首屏优先展示三项值得查看的变化：公司或主题、事实理由、数据时间、证据入口。
2. 长摘要默认折叠，未来事件单独显示。
3. 个股基础数据先返回；AI 分析独立请求、缓存与加载，失败不阻塞图表。
4. 若不同 tab 的数据开销较大，可按需加载。
5. 招募 3–5 位目标用户做探索性任务测试：用同一批数据找出应关注的公司，并解释理由。与简单表格或基线版本比较，尽量交替使用顺序。
6. 记录完成时间、遗漏、误判和需要额外核查的次数。小样本用于发现问题，不用于宣称普遍有效。

### 验收标准

- [ ] 用户首屏能看到重点变化及依据。
- [ ] 模型慢响应或失败时，基础行情和图表仍能显示。
- [ ] 有实际用户任务记录，以及据此做出的修改。

## 10. 推荐实施批次

### 第一批：可信度修复

完成数据状态、校验失败回退、结构化输出验证和因果措辞。运行相关离线测试及已有完整测试套件，加入有实际失败意义的回归用例。

### 第二批：核心排序实验

明确任务目标，锁定新测试数据，比较简单基线与改进版本，决定保留或删除哪些分项。不要先调大量权重，再寻找支持结果。

### 第三批：体验与验证

拆分加载、精简首屏、开展用户任务测试、发布 demo。整理一页结果说明：发现的问题、修改方式、指标变化与仍未解决的限制。
